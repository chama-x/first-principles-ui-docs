Stage 5: Physical Ergonomics

Keep Animations on the GPU & Choose the Right Easing

Enforce physical spring easing curves, strict GPU compositor property isolation (transform and opacity), and a 400ms Doherty response latency ceiling.

Full reference & code

Fast GPU scale · 150ms GPU

Fast GPU scale · 150ms GPU

Why this works

Animate only transform and opacity under 250ms instead of width, height, or padding.

GPU compositor isolation · Duration <= 250ms

Animating width or padding forces synchronous CPU layout reflow, dropping frames to stuttery lag. Restrict animations to GPU-composited transform and opacity with critically damped springs (zeta >= 0.85) settling under 350ms.

Spring Easings & Press States

Interactive Drills

Sluggish transitions and mechanical linear animations make digital interfaces feel cheap and unresponsive. Worse, using transition: all forces the browser engine to recalculate geometric layout on every animation frame, causing dropped frames and sluggish mobile scrolling.

  1. Spring Deceleration Curves: Mechanical linear transitions move at constant speed and stop abruptly, violating physical inertia. Physical objects decelerate smoothly into place. Easing curves like cubic-bezier(0.22, 1, 0.36, 1) mimic critically damped springs, providing instant feedback with a natural settle.
  2. Compositor Property Isolation: The browser rendering pipeline splits work into Layout, Paint, and Composite. Animating width, height, or margin forces continuous re-layout across the DOM tree. Modern interfaces must animate only GPU-accelerated compositor properties: transform, opacity, and color tokens.
  3. Doherty Response Budget: The Doherty threshold establishes that human interaction feels instantaneous when system feedback completes within 400ms. Choreographed animations where total duration plus delay exceeds 400ms introduce perceived drag.

Remediation

Isolate transitions to specific compositor tokens and specify high-performance spring easing:

/* Good: GPU-accelerated spring transition */
.btn-action {
  transition-property: transform, opacity, background-color, border-color;
  transition-duration: 200ms;
  transition-timing-function: cubic-bezier(0.22, 1, 0.36, 1);
}

.btn-action:hover {
  transform: translateY(-1px);
}

for (const el of allVisible) {
  const cs = getComputedStyle(el);

  // 1. Flag linear easing
  if (cs.transitionTimingFunction === "linear" && cs.transitionDuration !== "0s") {
    ctx.report("LAW_15_LINEAR_EASING", {
      property: "transition-timing-function",
      computed: "linear",
      threshold: "cubic-bezier(0.22, 1, 0.36, 1)",
    });
  }

  // 2. Layout thrash guard
  if (cs.transitionDuration !== "0s" && cs.transitionProperty === "all") {
    ctx.report("LAW_15_LAYOUT_THRASH_ANIMATION", {
      property: "transition-property",
      computed: "all",
      threshold: "transform, opacity, color, background-color, border-color",
    });
  }
}

What to Look For & How the Linter Fixes It

Visual signs in your UI and how the verifier guides your coding agent.

Visual Symptom
  • Animations feel robotic, jerky, or mechanical because they use linear timing functions.
  • Hovering or expanding cards causes stuttering, frame drops, and layout thrashing.
  • Transitions linger on screen for too long, making the application feel sluggish and unresponsive.
  • Buttons feel unresponsive because button-press feedback is delayed or missing.
Linter Check
  • transition-timing-function evaluates to linear on non-zero duration transitions.
  • transition-property contains 'all' or animates layout geometry properties.
  • Animation duration + delay > 400ms ceiling.

Agent Prompts & Oracles
